# Manifest Evaluations:
	Foundational work from earlier semesters was used to webscrape the Meta store to find apps that had the Eye-Tracking tag on the store, which ideally is accurate information. The foundational work found that there are significant discrepancies between what apps have the Eye Tracking tag on the store and what consent prompts users actually saw in the application. 
The initial focus of this project was to evaluate the Android Manifest files of apps available on the Meta Store that were free-to-play and compatible with the Meta Quest Pro headset. The Android Manifest file should contain all permissions and functionality that are used in the application. It is up to the developers to disclose this information in the manifest. A process explained in the Manifest Quick Access guide demonstrates the methodology used to extract the Android Manifests from ~30 of these Eye-Tracking apps. 
On the headset, the file for each application is called an APK(Android Package Kit) and contains everything generated by the headset on download and deployment. The APK was pulled and then decoded, and the manifest was manually copied to a separate file directory for each app. 
  Once the manifests were isolated, every .xml file was searched over by hand to find all of the eye tracking declarations in the form: <uses-feature android:name="oculus.software.eye_tracking" and <uses-permission android:name="com.oculus.permission.EYE_TRACKING"/>
Each app was then categorized into two categories: eye-tracking declaration present and declaration not present. Using these results in comparison to the foundational works’ manual evaluation of in-app consent prompts, it was found that only 65% of apps that had the manifest declaration also had in-app consent prompts. Additionally, if the manifest file contained the eye tracking declaration, it directly correlated to a tag being present on the store for that app. 
This begs the question that leads into the current semester's work: why are there apps that are supposedly using eye-tracking in app, not asking the user for consent to do so? Is eye tracking actually occurring?

# Current Work:
  Using the pool of previously audited apps, a process to analyze the contents of the native shared object (.so) files was developed and tested. The .so files contain the executable code for each application, and should contain all information related to sensor usage and related tracking capabilities, essentially what the application actually does at run time. 
  These files are formatted in ASCII and thus need to be translated into plain text for easy viewing and parsing using string libraries. The Python Script normalize.py will identify all decoded APK files within the directory provided, convert them into plain text files, and place each within a normalized/* folder unique to each application decoded package name. Each line within the normalized files will contain the offset of the original ASCII and the translated plain text.
  scan_normalized.py parses over all of the normalized .so files and searches for instances of keywords in the given search_terms.txt document. These terms are a curated list of almost all eye-tracking-related lines that could appear within the files. Then each term found is categorized into 5 eye-tracking use case groups: Foveated Rendering, Raw Data & State Collection, Biometric Signals & Metrics, Gaze Geometry & Interactions, and General Eye Tracking Enablement. For example, if an app is found to have an occurrence of a categorized Foveated Rendering search term exactly, it is categorized with high confidence. If the term matched is a substring of a categorized search term, such as "Foveated", it is given a medium confidence rating. Finally, if the term was found using the initial search terms and does not have a specific category to fit in, it is added to "General Eye Tracking Enablement" with a low confidence rating. For each term matched, a .json entry is added to the applications scan_matches.json file, and a line is added to the scan_summary.csv, which includes the term that was matched, its sorted category, the confidence level, and lines from the decoded example are stored. All of the JSON information is compiled into a master-results.txt file, where each app's data is stored.
  The master-results.txt file is parsed over using usage_summary.py to condense all of the .so file analysis findings into .csvs for easy visual data representation. The matrix_summary.py parses the app_functionality.txt file generated by the usage_summary. and combines the findings from the manifest evaluations' manifest_only_summary.txt for each application into one final, all-encompassing .csv file.

  Using another Python script, meta_store_scrape.py, the sample size of apps was increased to 106, to have around 50% of apps include the eye tracking tag on the store listing, and 50% not. The application went through the free listing of apps on the store and created a list of application names to download to the Meta Quest Pro. Completing the manifest evaluation process on a larger number of apps required a bash script to automate the decoding and scanning process. The apps listed by the script were downloaded to the headset manually, and Android Debug Bridge (ADB) was used to get a list of all packages on the headset. Each package had to be associated with a given application name and manually added to the packages-to-pull.txt file. 
  The bash script pull_decoded_packages.sh is used to pull all of the headset packages from the headset, decompile them, and store the files in the decoded-apks/* directory. A second bash script, separate_manifests.sh, is used to copy the Android Manifest (.xml) file for each app into the manifests/* directory. Finally, scan_manifests.py uses the search_terms.txt file, which contains the possible manifest declarations for eye tracking, and parses over every manifest, keeping note of the application name, and sorting them into a text manifest_only_summary document.

  This process was then completed on the new sample size of 106 apps, and these findings are being analyzed for poster presentations at the current moment.
